# instance_id — 实例号与事件 ID 布局

验证每个 wparse 实例的 `WP_INS_ID` 是否正确落进 `wp_event_id` 的实例段，从而保证**多实例同时运行不会产出重复 ID**。

## 背景

`wp_event_id` 是一个 64 位整数，布局固定为：

```text
 63            32 31        22 21                    0
+----------------+-----------+-----------------------+
|  秒 (32 bit)   | 实例(10)  |  每秒计数器 (22 bit)  |
+----------------+-----------+-----------------------+
```

- **秒**：Unix 时间戳，到 2106-02-07；在高位，所以按数值比较即时间序
- **实例号**：`instance_id - 100`，取值 `100..=1123`，共 1024 个实例
- **每秒计数器**：每实例每秒最多 4,194,304 条

唯一性完全由**实例号**保证：只要每个实例的 `WP_INS_ID` 不同，两个实例的 ID 段就互不相交，永远不可能重复。

历史上这里用的是「随机 63 位种子 + 进程内计数器」，两台机器在同一秒启动会生成完全相同的序列 —— 这正是本用例要防住的回归。

## 配置解析

`WP_INS_ID` 与 `WP_GLOBAL_TAGS` 走完全相同的解析链路：

1. 进程环境变量（`docker -e` / systemd）—— 优先级最高
2. `<work_root>/.env`
3. `<work_root>/.warp_parse/.env`

未设置时回退默认值 `100` 并打 WARN。**非法值（非数字、越界、首次发号后被改动）直接启动失败**，不会静默回退 —— 静默回退会让多个实例挤进同一个 lane，持续产出重复 ID。

## 运行

```bash
./run.sh
# 或调小规模
LINE_CNT=200 ./run.sh
```

## 断言

| 步骤 | 验证内容 |
| --- | --- |
| 1 | 未设置 `WP_INS_ID` → lane=0（默认实例号 100）；每条记录都带 `wp_event_id`；ID 唯一；秒段贴近当前时间 |
| 2 | `WP_INS_ID=101`（进程环境）→ lane=1 |
| 3 | `.env` 里 `WP_INS_ID=102` → lane=2（不设进程环境变量） |
| 4 | `.env=102` 且进程 `=103` → lane=3（进程环境优先） |
| 5 | `.env` 同时提供 `WP_INS_ID` 与 `WP_GLOBAL_TAGS` → 两者都生效，全局 tag 覆盖每条记录 |
| 6 | `WP_INS_ID` 为 `99` / `0` / `1124` / `abc` → 启动失败，且错误信息提到 `WP_INS_ID` |

lane 段的计算：

```bash
lane = (id / 2^22) % 2^10
```

ID 是 19 位整数（约 `7.7e18`），超过 `2^53`，`awk` 与 `sort -n` 会丢精度，所以脚本里统一用 `bc` 做整数运算。

## 下游注意

`wp_event_id` 全程 `u64` 并以字符串输出，wparse 侧不涉及有符号数。但下游列类型会影响可用性：

- 有符号 `BIGINT` / `Int64`：2038-01-19 之后超出该列范围
- 字符串列或 `BIGINT UNSIGNED`：可用到 2106-02-07
- `VARCHAR` + `ORDER BY`：字典序仅在位数相同时成立，ID 约 2044 年从 19 位变 20 位，排序请用 `CAST(... AS BIGINT UNSIGNED)`
